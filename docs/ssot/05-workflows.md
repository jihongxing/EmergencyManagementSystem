# 自检与现场抽检双轨

状态：`FROZEN`（软件流程）；临时检查合法情形属于 `EXTERNAL INPUT`。来源：交接稿 1.2、4.9、9、14 节及后续扫码启动、最小数据边界决定。

**企业轨：**场所/对象登记、扫码识别 → 自检 → 发现问题 → 整改证据 → 自主复查。人员、时间、结果、证据及问题关联实际对象与执行时有效的规则版本；企业自检正常不等于行政检查合格。

**行政轨：**检查人员现场扫描设施二维码 → 系统识别对象与所属场所 → 核对检查人员身份、部门监管关系、适用事项及本次启动和程序依据 → 发起临时抽检并形成独立记录与证据 → 发现问题时记录整改要求及后续复查。现场发起无需预建任务、逐次预录计划或部门派单；二维码不是检查权力来源。无法确认上述依据时不得形成正式行政检查记录。具体合法启动情形须由试点部门提供依据后配置。

两轨共用场所和对象身份，证据只在授权范围内关联；记录来源、权限、检查结果、启动依据与审计历史分开，不互改或相互覆盖。事实变更留痕，不因新规则覆盖旧版本。处罚首期只关联平台外依法形成的文书，不制作处罚裁量、决定或执行流程；行政处置不是每次抽检的必经步骤。规则权威见 [02-authority](02-authority.md)，人员及可见性见 [04-access](04-access.md)。

订阅与否不改变上述企业自检、整改、复查闭环及必要监管交互能否完成；订阅只提供企业内部跨场所工作台等便利，详见 [01-product](01-product.md)。

## 记录的最小边界

企业记录和行政记录分别标识来源、执行人、场所与对象、执行时间及当时有效的规则/事项版本；证据关联所属记录，问题与整改/复查保留来源及前后关联。后续规则或对象、二维码关系变化不覆盖既有事实；纠错保留变更审计。首期行政人员现场扫码启动不要求预建检查计划、任务或派单实体。上述是数据约束，不要求各概念各建一张表；实现划分见 [06-technology](06-technology.md)。
