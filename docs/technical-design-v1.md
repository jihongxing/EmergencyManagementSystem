# V1 详细技术方案（待评审）

状态：`PARTIALLY APPROVED TECHNICAL DESIGN`。日期：2026-09-28。单 App 工作区和 P0-01 最小工程基线已批准，唯一正文见[技术 SSOT](ssot/06-technology.md)；其余建议仍待评审。本文不代表试点行政资料已取得或生产供应商已确定；后续按[文档治理](GOVERNANCE.md)及[文档 -> 契约 -> 代码](../AGENTS.md)推进。

## 1. 目标与交付边界

首期交付一个 Android/iOS Flutter App（多个按身份隔离的工作区）、部门管理 Web、独立的组织购买 Web 入口、一个后端和两类存储：

| 入口 | 用户 | 首期能力 |
| --- | --- | --- |
| 同一个 Flutter App（Android/iOS） | 单位管理员、单位执行人员、行政检查人员 | 登录后按当前身份进入企业或行政现场工作区：企业侧管理本组织成员/场所/对象、自检、整改、复查及历史，管理员可用付费跨场所工作台；行政侧扫码识别对象、核验本次条件、形成独立行政记录及整改要求和复查 |
| 桌面响应式 Web | 部门管理员及获授权的部门人员 | 本部门人员与监管范围配置、待处理绑定、已授权范围内的记录查看与管理 |
| 独立组织级 Web 购买入口 | 单位管理员 | 组织订阅、订单与权益查询；不建设企业桌面业务端 |

首期只上线单县、单部门的日常业务，不实现市/省、跨部门或乡镇/街道操作；数据模型保留多个部门与场所关系的可能性，但不预授予访问权限。企业免费闭环和必要监管交互必须可用；订阅只控制本组织的跨场所汇总和批量便利。依据：[产品](ssot/01-product.md)、[权限](ssot/04-access.md)、[双轨](ssot/05-workflows.md)、[技术](ssot/06-technology.md)。

“双端”指 Android 和 iOS 两个平台，不指企业端与行政端分成两个 App。工作区入口按身份呈现，但不是权限边界：后端每次读写仍须核对当前组织、角色、分配范围、监管关系及行政操作所需依据；两轨记录保持独立，不因共用扫码和客户端而互改。

## 2. 推荐技术栈

P0-01 核对与用户确认已完成，见[工程基线](engineering-baseline.md)。下表中 Vue/TypeScript/Vite、Go net/http/显式 SQL、单 App 及 PostgreSQL 方向按技术 SSOT 执行；驱动、迁移工具、文件供应商、凭据、支付及生产部署等仍待相应任务确定。

| 层 | 建议 | 选择理由与边界 |
| --- | --- | --- |
| 移动端 | 一个 Flutter / Dart App；按企业与行政现场工作区划分功能模块，声明式路由和显式状态管理 | 同一应用发布 Android/iOS，扫码、拍照与现场表单共用基础能力；工作区入口按身份呈现，平台权限和分发规则单独处理 |
| 部门 Web 与购买页 | Vue 3 + TypeScript + Vite；成熟组件库用于表格、表单、筛选 | 管理端以密集列表和审核操作为主；购买页与监管端使用独立路由和权限边界，不共享业务会话 |
| API | Go 模块化单体，标准库 `net/http` 路由与中间件；OpenAPI 描述对外 HTTP/JSON 接口 | 首期不引入微服务；统一授权、审计和事务边界；不把路由或 ORM 框架作为产品依赖 |
| 数据 | PostgreSQL；显式 SQL + 轻量数据库驱动；版本化 SQL 迁移 | 能用事务、外键、唯一约束保护关键关系；迁移与应用版本一起发布 |
| 证据文件 | 与业务库分离的 S3 兼容对象存储；本地开发用隔离的兼容服务 | 数据库只保存对象键、摘要、状态及记录关联；具体生产供应商和部署方式待技术选型与合规审查 |
| 测试/交付 | Go 单测与集成测、Flutter 测试、Web 测试、容器化开发环境、CI | 契约检查与模块测试一起进入合并门禁；生产部署拓扑视试点运行条件确定 |

**版本策略：**创建工程时核对各技术的官方维护窗口并锁定具体稳定版本、依赖校验和升级节奏；本文不把未经验证的版本号写成已批准事实。首期避免 Redis、消息队列、搜索引擎、GIS 平台和复杂工作流引擎；若实际负载证明必要，再提出单独变更。扫码库、状态管理库、UI 组件库、迁移工具在首个模块契约与工程脚手架阶段锁定，避免现阶段预设过多依赖。

## 3. 总体结构

```text
一个 Flutter App (企业 / 行政工作区)   Web (部门管理 / 企业购买)
                    | HTTPS JSON API |
                    v                v
             Go 单体：认证与授权、业务模块、审计、文件访问、权益
                    |                          |
              PostgreSQL                 私有对象存储
                    |
          支付适配接口（供应商待定）
```

后端按 `identity`（组织/成员/会话）、`site`（场所/对象/二维码）、`jurisdiction`（区划与监管绑定）、`authority`（外部依据/规则版本）、`inspection`（企业与行政双轨）、`evidence`、`subscription`、`audit` 划分代码边界。模块内拥有自己的数据操作，跨模块通过应用服务和事务协作，不让客户端直接写库。允许一个部署进程；模块不是独立服务，也不要求一个概念一张表。

建议工程结构（路径为工程建议，非已冻结接口）：

```text
apps/mobile/              一个 Flutter App，发布 Android/iOS，含隔离工作区
apps/admin-web/           部门管理 Web 与隔离的组织购买路由
backend/cmd/server/       Go 进程入口
backend/internal/         模块与共享基础设施
backend/migrations/       PostgreSQL 迁移
constras/                 既有 Markdown + JSON 判定及后续模块契约
scripts/test/             文档与契约治理检查
```

## 4. 数据与一致性设计

- **组织与身份：**组织、成员、账号、角色分配、场所分配、授予/撤销审计；实施人员线下核验并开通首位管理员。管理员仅管理本方。成员停用后所有新请求即时拒绝，既有记录执行人保持原值。
- **场所与对象：**场所保存实际地址、经核验的区划代码/来源、组织责任关系及申报/行政确认状态；对象持有稳定 ID、类型、场所归属和生命周期。二维码使用随机不可猜测令牌映射到对象，存储令牌摘要及生效/停用时间；补打、停用、更换保留映射历史。二维码不携带检查权限或永久检查表。
- **监管关系：**区划数据集、部门职责范围规则、匹配运行和场所监管关系均记录来源、版本、核验状态与有效区间。当前关系与历史关系分离；变更时在事务中结束旧关系并建立新关系，不覆盖过去检查所指的场所、对象及当时关系快照。将来可容纳多部门，但 V1 只启用经核验的单部门配置。
- **规则与记录：**适用事项和规则以不可变版本及有效时间保存，区分外部权威与企业内部安排。执行记录至少引用场所、对象、执行人、时间、来源轨、当时的事项/规则版本和已核验依据；企业与行政记录逻辑隔离，任何一轨不能原地修改另一轨。问题、整改证据、复查引用原始来源记录；纠错采取带审计的更正，不静默覆盖。
- **证据：**对象存储桶私有；上传初始化生成短时受限写入许可，完成后服务端验证大小、类型、摘要及所属记录再标记可用。下载先检查记录级授权及字段/证据共享规则，再由服务端代理或发放短时受限读取许可；仅知道对象键不能读取文件。文件状态与业务事务不构成分布式原子提交，采用待确认状态、幂等完成及过期清理，不显示孤立上传为正式证据。
- **订阅：**订单、支付通知去重、权益区间按组织记录。服务端已核实的支付或退款事件才可更新权益；客户端付款结果只触发查询。到期/退款停止便利功能，不删除免费记录。组织 ID、记录来源、对象 ID 与执行时版本均设置索引和约束；枚举/状态由代码与数据库迁移共同约束。

不在业务表用单一 `confirmed` 布尔值混合“企业申报”“行政确认”“外部依据已核验”“监管已绑定”；这些是不同事实、不同来源和不同时间线。敏感身份材料仅保存最低必要字段与受控引用，具体保存期限和共享字段需按试点资料确定。

## 5. 核心链路

**场所申报与自动绑定。** 单位管理员申报实际地址和责任材料，允许先进入本组织自检。系统只使用已核验的区划资料和部门监管范围进行确定性匹配：属于试点县、规则有效且唯一命中、无重复/争议/冲突时，生成带依据和版本的当前绑定；其余进入待处理，不标为已绑定。人工核验须记录人、理由、依据、时间；不能以人工操作绕开部门职责核验。地址、责任或范围版本变化触发当前关系重算并保留旧关系。外部地址解析供应商未定时，可先接受经核验的结构化区划输入，不做模糊坐标推断。

**单位自检。** 鉴权及分配范围检查 -> 有效码解析对象 -> 加载适用的已核验规则版本或明确标识企业内部安排/待确认 -> 提交独立企业记录 -> 问题 -> 整改证据 -> 自主复查。不存在已核验法定规则时，不展示法定合规结论；业务流程可在适当标识下保留企业自检事实。免费组织完整使用此链路。

**行政现场抽检。** 行政人员现场扫码 -> 对象与场所解析 -> 服务端逐次检查人员身份/资格、部门职责和当前监管关系、事项适用性、本次启动和程序依据 -> 符合全部条件时写入独立行政检查记录，后续记录整改要求及复查。无需预建任务、计划或派单。任一依据缺失、未核验或扫码失效，只能停在待核验状态，不生成或显示正式行政记录。扫码不是授权。

**组织订阅。** 单位管理员在独立 Web 入口创建组织订单 -> 支付适配器处理渠道请求 -> 服务端验签、金额/订单/组织核对、通知去重 -> 更新组织权益 -> Flutter/Web 查询最新权益。Web 入口仅是设计起点；应用商店和地区规则核验前，Flutter 不提供站外支付引导。付款失败、通知延迟、退款和到期均不影响逐场所免费闭环。支付供应商、开票、退款和续费细则仍为[待决事项](OPEN.md)，集成前需确认。

## 6. 身份、安全与接口

- 首期采用实施人员线下核验开通首位管理员，之后本方管理员邀请/开通本方成员；不开放公众自助认领。具体登录凭据选型在上线前经试点身份保障要求核验；不把账号角色当成执法资格。
- Web 使用安全、HttpOnly、SameSite 的会话 Cookie，并做 CSRF 防护；移动端使用短时访问凭据及可撤销的刷新凭据，安全存储并支持设备退出。服务端每次读写重新核对当前成员/角色、组织/部门、场所/对象分配和记录所属；权限变更不得仅依赖过期令牌自然失效。
- 每次证据下载与导出独立授权。行政查看企业字段/照片按已核验共享清单逐字段限制；未取得清单时默认不可见。记录响应与审计日志不输出无权查看的附件地址或敏感原文。生产环境 TLS、密钥托管、凭据轮换、最小权限数据库账号和独立测试数据。
- 接口统一约定 JSON 错误结构、请求追踪 ID、分页/筛选、幂等键和状态码；提交、支付通知、证据完成等重试操作必须幂等。服务端确认前，客户端仅显示“提交中/待确认”，超时先按幂等键查询结果，绝不把网络失败当成正式完成。
- 每个模块编码前在 `constras/` 增加对应机器可读 OpenAPI 及必要的 JSON Schema/状态测试数据，写明请求、响应、权限、错误、依据条款和外部资料缺失行为；保持现有 Markdown 的验收依据及 JSON 判定子集。生成类型可作为减少漂移的手段，但业务授权必须由服务端测试覆盖。

## 7. 部署、运维与质量门槛

开发环境采用 PostgreSQL、私有对象存储兼容服务、Go API、Web 构建与 Flutter 调试；测试环境与正式环境隔离。生产最小拓扑是 TLS 入口、单体 API、PostgreSQL、私有文件存储与受控备份，不预设某云厂商。数据库迁移前备份并在预发环境演练；应用升级考虑兼容窗口。数据库定期备份和恢复演练，文件对象及元数据一起纳入恢复计划；具体 RPO/RTO、留存期、部署地区和安全等级待试点及合规要求确认。

结构化日志记录请求 ID、主体、场所/对象引用、动作结果和错误码，审计单独记录开通/撤权、外部依据核验、绑定改动、行政启动、记录更正、证据访问及权益变更；避免记录个人敏感信息和文件内容。监控 API 错误率/延迟、正式提交失败、绑定待处理、上传失败、支付回调失败和备份结果。生产权限、存储隔离与备份恢复要有可执行验证，不以“部署成功”替代验收。

测试按风险分层：治理脚本解析 `constras/*.json`；单测覆盖确定性匹配、轨道隔离、授权、规则版本和权益；PostgreSQL 集成测验证事务、历史与幂等；API 测试覆盖跨组织/跨场所越权、未核验依据、证据下载和支付伪通知；Flutter/Web 端到端验证扫码到结果、网络中断重试、免费闭环及订阅到期。正式行政成功路径只使用真实已核验试点输入；测试环境可用明确隔离的模拟材料验证功能，但不得流入生产。

## 8. 实施顺序与停止条件

1. **工程基础：**确定受支持版本、项目结构、迁移/测试/CI，建立身份与组织开通、最小鉴权、审计基础；为首个模块补 OpenAPI 与数据契约。
2. **企业免费链路：**场所、对象/二维码、分配、自检、证据、问题整改、复查与历史。先用隔离测试资料跑通全链路，不把模拟依据作为生产规则。
3. **监管关系与行政链路：**导入经核验的区划、职责、事项与程序材料；自动匹配、待处理、逐次授权、现场扫码、独立行政记录和部门 Web。资料缺失时仅交付待核验状态与阻断逻辑，不能宣布正式行政链路可上线。
4. **订阅便利与购买：**跨场所工作台、批量提醒/分配、组织权益及服务端支付确认；支付渠道、退款/开票/续费和应用分发规则确认后再做真实交易与上线。
5. **上线验证：**跨角色授权/共享清单、历史版本、并发重试、证据隔离、备份恢复与真实试点依据核验；按试点运行条件决定拓扑、容量和运行指标。

**尚需确认的技术决定：**数据库驱动/迁移工具、对象存储兼容策略与供应商、身份凭据方案、生产部署、支付服务商和应用分发路径。Web 与 Go API/SQL 最小基线已通过 P0-01 确认，其他建议不因此自动冻结；行政事项、法定范围、共享资料和临时检查依据只能由有权方提供并核验。
