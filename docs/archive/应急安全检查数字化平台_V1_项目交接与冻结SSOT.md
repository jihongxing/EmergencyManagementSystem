# 1. V1 产品定位 —— FROZEN

正式冻结的 V1 定义：

“面向辖区安全生产与应急管理的‘自检 + 抽检 + 整改 + 行政检查’数字化共同底座。”

核心不是“消防巡检 App”、不是“通用设施巡检 SaaS”、也不是“政府检查 App”。产品要建立一个辖区级安全检查共同数据底座：企业/物业等被监管单位持续产生自检数据；具有法定监管职责的行政部门在同一底座上进行抽检、监督检查、整改复查及依法产生的行政处置记录；上级行政层级按权限查看辖区汇总和检查历史。

## 1.1 核心业务结构 —— FROZEN

企业/物业是底层自检数据的主要生产者；行政管理部门是监督、抽检、整改、执法记录的产生者。两类记录共用同一底层对象、证据与历史体系，但必须在数据模型与审计语义上永久区分。

| 层级 | 主体 | 主要行为 | 数据结果 |
| --- | --- | --- | --- |
| 被监管单位 | 企业 / 物业 / 其他纳管单位 | 对象登记、自检/巡检、发现问题、自主整改、自主复查 | 自检记录、问题记录、整改证据、复查记录 |
| 基层监管 | 乡镇/街道及有法定职责的行政部门 | 抽检、监督检查、问题处置、复查 | 行政检查记录、整改要求、行政处置记录 |
| 县/区监管 | 县级/区级相关监管部门 | 辖区总览、计划、抽检、监督、分析 | 辖区监管视图与检查档案 |
| 市级及以上 | 上级相关行政部门 | 按法定权限查看汇总、检查与辖区数据 | 跨辖区监管视图 / 统计 / 检查记录 |

## 1.2 核心业务闭环 —— FROZEN

场所及对象登记 → 数字身份/二维码 → 企业/物业自检 → 问题发现 → 自主整改 → 自主复查；现场检查人员扫码发起临时抽检 → 独立行政检查记录 → 必要时形成行政整改要求与复查记录 → 依法产生的行政处置/处罚文书关联 → 县级监管视图与历史追溯。行政处置并非每次抽检的必经环节，首期只关联外部文书，不在平台内制作处罚决定。

关键原则：企业自检记录与行政检查记录不能互相覆盖、修改成同一种记录，也不能把“自检正常”直接等同为“行政检查合格”。它们属于不同来源、不同权限、不同法律/管理语义的事实记录。

# 2. 三个核心原则 —— FROZEN

原则一：企业/物业自检是底层数据生产机制。企业/物业不是“附属端”，而是平台持续产生安全检查事实的主要来源。

原则二：行政部门的抽检/检查建立在同一个数据底座之上。行政部门可以查看被监管单位自检历史，并在法定职责范围内据此安排检查、抽检、整改、复查和行政处置；行政记录独立留存。

原则三：行政层级天然构成产品扩散网络。单位 → 乡镇/街道 → 县/区 → 市级，上级按照权限观察下级；平台的增长单位应尽量从“单个企业”提升到“一个行政辖区”。

# 3. Authority SSOT —— FROZEN

## Authority-01：对象权威

正式冻结：企业/物业负责自登记、自更新、真实性负责；法定登记/备案数据作为外部权威来源；有监管职责的行政部门拥有依法核验、纠正、确认的监管权。平台不凭空创造设施。

因此，“对象登记”采用双层语义：企业/物业拥有申报权；具有法定监管职责的行政机关拥有依法核验、纠正、确认的监管权。系统可以存在“自登记 / 待核验 / 已确认 / 已注销 / 监管调整”等状态，但不得把企业输入直接伪装成行政确认事实。

## Authority-02：规则权威

正式冻结：检查清单必须来自法律法规、规章、国家/行业标准以及有权限的行政主体依法公布的行政检查事项。平台不自行制定监管标准。平台只负责：采集 → 结构化 → 版本化 → 执行。

任何检查模板都应保留来源和版本语义，包括：检查事项、适用对象、法律/标准依据、发布主体、版本号、生效日期、失效日期（如有）、检查项及证据要求。

历史记录必须绑定当时实际执行的规则/模板版本，未来规则升级不得覆盖历史检查事实。

## Authority-03：周期权威

正式冻结：企业自检以法定最低要求为底线，再叠加企业自身风险管理要求；行政检查须有合法主体、事项及适用的计划或依法允许的临时检查情形和程序依据。平台不自行决定“这个设备每月检查一次”。首期部门端以现场扫码发起临时抽检为入口，不以预建计划、任务或派单作为每次抽检的系统前置操作。

平台至少需要区分三种频次来源：法定最低频次、企业自检频次、行政检查计划频次（如适用）。企业可以比法定最低要求更频繁，但不得通过平台把低于法定要求的频次伪装成合规频次；现场临时抽检不得仅凭扫码或检查事项存在就推定具备合法启动依据，具体情形须经试点部门核验。

## 3.1 Authority 核心逻辑 —— FROZEN

“谁负责这个对象，由责任主体和法定登记关系确定；检查什么，由法律法规、标准和有权机关公布的行政检查事项确定；周期性自检与计划性检查的频次分别来自法定要求、企业制度和行政检查计划。现场临时抽检不以预建任务启动，但仍须记录合法主体、事项、人员及适用的启动和程序依据。平台负责形成可执行、可追溯、不可混淆的检查记录。”

# 4. 现实世界对象与二维码 —— FROZEN / 产品原语

消防柜只是最初的发现入口，不是产品定义。产品应支持“需要被检查的现实对象”，但 V1 仍以安全生产/应急管理检查对象为边界，不扩张为通用资产管理平台。

核心动作：登记对象 → 生成唯一数字身份 → 分配二维码 → 现场扫码识别 → 根据检查类型、对象类型、适用事项及权威规则版本加载检查清单 → 记录结果与证据 → 形成对象生命周期历史。行政人员扫码可发起现场临时抽检，不要求预建任务。

二维码不是产品本身，也不是固定表单的永久绑定器。二维码主要负责把现实对象稳定映射到对象数字身份；最终展示的检查内容由“对象 + 本次检查类型或已有任务（如有）+ 适用检查事项 + 权威规则版本”共同决定。二维码本身不构成行政检查授权。

## 4.1 一个对象的最低数据关系 —— FROZEN CONCEPT

| 对象 | 示例 | 必须关联的数据 |
| --- | --- | --- |
| 检查对象 | 消防设施、配电柜、有限空间等 | 对象类型、所属单位、位置、责任关系、生命周期状态 |
| 数字身份 | Object ID / QR | 唯一标识、二维码状态、对象映射关系 |
| 企业自检 | 月度/日常自检 | 检查人员、时间、结果、证据、问题 |
| 整改 | 企业自主整改 | 问题、责任人、期限、整改证据、复查 |
| 行政检查 | 现场临时抽检/监督检查 | 发起情形与依据、执法/检查人员、检查事项、现场结果、证据 |
| 行政处置 | 整改要求/处罚等 | 行政机关、法律依据、决定/文书关系、执行状态 |

## 4.2 实际场所与组织的职责边界 —— FROZEN

V1 以“实际场所”为辖区归属和监管绑定的基本单位；企业/物业组织作为责任与人员管理主体。场所与检查对象不同：场所承载所在地及监管关系，检查对象位于场所内。企业/物业组织管理其负责场所中的人员和业务，不得仅凭组织登记地址推定所有场所的辖区归属或监管部门。

本条冻结基本单位和职责边界；首期角色见 4.5 节，首位管理员开通路径见 4.6 节，场所申报与异常处理见 4.7 节，数据可见性边界见 4.8 节；具体权威资料与字段级实现仍待核验。监管绑定的默认方式见 4.4 节。

## 4.3 V1 首期实施范围 —— FROZEN

V1 从单个县级辖区、单个具有相应职责的监管部门启动，先跑通该辖区内企业/物业组织、实际场所、自检与整改、该部门行政检查的业务闭环。市级、省级管理账号与跨部门操作不在 V1 首期实现范围；只保留支持后续扩展的组织、辖区和监管关系模型，不因预留模型而默认开放跨部门数据或赋予上级部门操作权限。

首期单位和场所的申报与核验原则、数据可见性边界及实施方式见 4.7 至 4.10 节。具体试点县、部门监管范围的权威依据、首批检查事项和法定频次仍须取得有效材料后核验；本条不等于已选定试点县或具体监管部门。

## 4.4 场所与监管部门的自动绑定 —— FROZEN

V1 首期以系统自动匹配为默认方式，不要求监管部门逐一手工绑定场所。只有场所的实际地址明确落入试点县级辖区，且场所明确符合该监管部门已确认的监管范围规则时，系统才自动建立该部门与场所的监管关系。地址或监管范围不明确时，转人工确认，不得将待确认关系标为已绑定。

自动绑定只确定场所与部门的监管关系，不自行赋予行政检查事项、生成行政检查任务或推定检查结论。异常处理和关系变更原则见 4.7 节；地址解析方法及监管范围规则的具体权威依据、配置细节仍为 OPEN。

## 4.5 V1 首期最小用户角色 —— FROZEN

首期仅设四类日常业务角色；同一人可兼任其组织内的管理员与执行角色，不另设市级、省级或跨部门角色。

| 角色 | 首期权限边界 |
| --- | --- |
| 单位管理员 | 管理本企业/物业组织的成员；登记和管理本组织负责的场所及检查对象；给成员分配本组织场所内的自检、整改、复查工作 |
| 单位执行人员 | 在被分配的本组织场所执行自检、整改、复查并提交记录和证据；不得管理本组织其他成员或形成行政检查记录 |
| 部门管理员 | 管理试点县唯一监管部门的成员及本部门监管范围配置的操作权限；不以预建任务或派单作为临时抽检前提，不得自行扩大部门法定职责 |
| 行政检查人员 | 在本人身份、本部门监管关系、适用事项及本次启动依据核对后，可现场扫码发起临时抽检、进行复查并提交独立记录；不得修改企业自检记录 |

平台角色仅代表系统操作权限，不等同于法定代表人、安全生产管理人员资格或行政执法资格；现场行政检查仍须另有合法主体、事项、人员及启动和程序依据。角色授权和撤销留痕，撤销后不得继续操作，但历史记录保留原执行人。

## 4.6 首位管理员开通的最短路径 —— FROZEN

试点实施时，由实施人员依据线下确认的单位授权材料和部门指定材料，分别建立企业/物业组织、试点监管部门及各自首位管理员账号，记录材料来源和开通人。实施人员不作为日常业务角色，也不代替组织或行政机关确认法定职责。后续由各自管理员在本组织/部门内添加成员、分配角色；首位管理员更换经线下确认后办理。首期不建设公众自助认领、电子证照集成或多级审批流。账号开通不等同于场所行政确认或人员执法资格确认。

## 4.7 场所申报、匹配与异常处理 —— FROZEN（产品流程）

单位管理员申报本组织实际负责的场所，记录名称、实际地址、责任关系及其证明材料；场所始终区分“单位申报”与“行政已确认”，单位自检不以行政确认作为前置条件。仅当实际地址明确落入试点县，且明确命中经试点部门确认的监管范围规则时自动建立监管关系，并保存匹配依据及规则版本；不等同于行政确认场所申报事实。地址不明、监管范围不明、重复场所或责任关系有争议时进入待处理列表，人工确认记录操作人、理由、依据和时间；不明确时不得标为已绑定。地址或责任关系变化时重新匹配，旧关系和记录保留。

首期维护试点县的地址归属数据和已确认的部门适用范围，不建立逐场所审批流；具体地址解析方案、权威资料和部门职责范围须在试点落地前核验。

## 4.8 首期数据可见性 —— FROZEN（产品边界）

单位仅查看和操作本组织负责场所及本组织记录；单位执行人员还受其被分配场所或工作范围限制。试点部门仅查看已确认归其监管的场所及在其法定职责和数据共享范围内所需的自检、问题、整改、复查记录，并管理本部门独立的行政检查记录；部门检查人员的写入范围受其身份和本次检查的合法事项约束。系统存储不构成部门查阅授权；具体字段与证据的共享范围仍须依据试点部门的有效授权资料核验。无市、省级账号和跨部门默认可见性。

## 4.9 对象身份、规则与双轨闭环 —— FROZEN（产品流程）

单位在场所下登记检查对象，系统生成稳定对象 ID 和二维码；扫码识别对象后，按本次检查类型和已核验有效的规则版本加载适用清单。首期支持二维码补打、停用、更换并保留映射历史；二维码不永久绑定固定表单。

检查事项与模板只录入已核实的来源、适用范围、生效时间及版本，历史记录保留执行时版本。企业自检安排与行政检查依据分开管理，平台不自创法定频次；无权威依据的清单或周期标为待确认，不作为合规或合法检查依据。

企业端闭环为自检 → 问题 → 整改证据 → 自主复查。部门端以行政检查人员现场扫描设施二维码启动临时抽检；系统识别所属场所，核对人员身份、监管关系、适用事项及本次检查的启动和程序依据后，形成独立行政检查记录与证据；有问题时记录整改要求及后续复查。首期不要求预建行政任务、部门派单或逐次预录计划，也不把扫码视为法定授权；无法确认上述依据时不得形成正式行政检查记录。具体依法允许的临时检查情形及现场程序须由试点部门提供有效依据后配置。

两轨共享场所和对象身份，证据按权限关联，不互改记录。行政处罚首期仅关联平台外依法形成的文书，不建设处罚裁量、决定或执行流程。重要授权、绑定、规则及事实记录的变更留痕，不覆盖历史。

## 4.10 首期技术形态 —— FROZEN（选型方向）

首期采用监管部门桌面响应式 Web 管理端、Android/iOS 双端 Flutter App（现场扫码及移动业务）、模块化单体 Go 后端、关系数据库和证据文件存储。Flutter App 承载企业/物业现场自检及部门现场抽检；监管部门的查看与管理在 Web 端完成。首期不做微服务、复杂工作流引擎或跨部门数据交换。具体 Web 框架、Go 框架、数据库、存储和部署方案留待技术设计，不以本条推定已完成适配或部署验证。

# 5. 多行政部门监管 —— FROZEN ARCHITECTURAL DIRECTION

一个企业/物业可能同时接受多个具有不同法定职责的行政管理部门监管。因此平台的主体模型不能假设“一个企业只有一个监管部门”。

建议形成：一个主体 + 多监管部门 + 多检查事项 + 统一对象/证据/历史底座。每个监管部门拥有各自的法定事项、权限、任务和行政记录，但共享同一主体和可依法共享的基础对象数据。

V1 商业切口仍锁定安全生产/应急管理，不主动扩成综合城市治理平台。多部门是架构扩展能力，不是 V1 对外定位。

同一对象可被多个部门关注，但每个部门看到的范围必须由法定职责、权限和数据共享规则决定；不能把“平台能存储”误写成“任何部门都有权查看”。

# 6. 目标辖区模型示例 —— 概念示例

用户提出的安徽省 / 滁州市 / 来安县场景作为产品规模示例，而不是当前已核验的现实统计数据：假设某县级辖区有 10 个乡镇、约 2000 家企业、约 3000 个小区，共约 5000 个纳管单位。

在该概念模型下：每个企业/物业建立自己的检查对象及巡检人员；持续产生自检/巡检记录；县级相关监管部门按权限查看辖区纳管场所的自检、问题、整改与复查记录，并进行行政抽检/监督检查。乡镇/街道和市级相关部门按权限查看辖区数据属于后续扩展示例，不属于 V1 首期交付范围。

该模型的关键不是“5000个客户”，而是“一个县级辖区形成一个共同数据网络”。

# 7. 市场竞品调研 —— 截至本轮调研

结论：市场并非空白。已经存在“企业自检 + 政府检查”的成熟实践，也存在企业安全生产 SaaS、设施巡检软件、综合监管平台等多条产品线。机会不在于宣称“没人做”，而在于将已验证的核心模式做得更轻、更标准、更易于以辖区为单位复制。

## 7.1 竞品一：北京“企安安”

公开资料显示，“企安安”已被北京市用于生产安全事故隐患排查治理，形成企业自查与政府检查共用的信息化体系。北京相关区县公开材料展示了企业自查、部门/属地检查、隐患整改等数据闭环。它是目前与本项目核心模型最接近的市场验证。

重要观察：企安安更接近“地方政府主导建设/采购的监管系统 + 配套技术/服务”，而不是典型的按企业订阅收费的纯 SaaS。

## 7.2 竞品二：企业安全生产 SaaS

国内存在大量企业安全生产数字化产品，常见能力包括双重预防、隐患排查、移动巡检、企业安全台账、园区/区县平台等，商业模式包括产品租赁、买断、项目合作、代理渠道等。

与本项目差异：这类产品通常以“企业/集团”为主要付费客户，而本项目 V1 更强调“辖区政府作为 Anchor Customer，企业/物业作为纳管单位和数据生产者”。

## 7.3 竞品三：二维码/设施巡检软件

消防、设备维保、设施管理领域已经广泛存在“点位二维码 + 检查项 + 异常 + 工单/整改 + 生命周期记录”的产品形态。

因此 QR、动态检查表、巡检历史本身不是核心壁垒。真正的差异点应放在：权威规则、企业自检与行政检查的同底座关系、辖区级分级监管、法定来源追溯以及跨行政部门可扩展性。

## 7.4 竞品四：综合监管/跨部门监管平台

政府侧已有“双随机、一公开”、跨部门综合监管、“一业一查”、移动监管、检查结果归集等大型平台与项目。

与本项目差异：这些系统通常是大型政府信息化工程；本项目 V1 不与之正面竞争，不从“综合城市治理”切入，而先把“安全检查共同底座”做成可复制的辖区产品。

# 8. 商业模式 —— 当前为 PROPOSED / 待最终冻结

以下商业模式是本轮基于竞品调研形成的建议，不属于本轮已经批准冻结的 SSOT。Codex 后续应继续调研、验证成本与采购路径后再提交 Founder 冻结。

建议模式：B2G2B —— Government Anchor + Enterprise Network。V1 首期已批准以“县级试点采购、企业/物业基础使用随试点覆盖”作为商业验证路径；不开发收费、订阅或结算功能。这是待市场验证的经营假设，不代表已经确认采购主体、采购程序、价格或续费模式；下表其他扩展收入仍为 PROPOSED。

| 收入/关系层 | 建议模式 | 原因 |
| --- | --- | --- |
| 政府端 | 首期验证以县级辖区为采购单元；其他辖区及具体部署、运行维护、规则/数据服务的采购方式待调研 | 与辖区监管权力和推广机制一致；政府是网络 Anchor Customer 的假设待验证 |
| 企业/物业基础端 | 基础监管使用原则上不单独收费，随辖区采购覆盖 | 降低辖区纳管阻力，把企业变成数据生产者而不是逐个销售对象 |
| 企业增强端 | 可选付费高级能力：集团、多场所、内部管理、审计、培训、API、第三方协同等 | 形成 B2B 增值收入，但不影响基础监管功能 |
| 监管部门扩展 | 新部门按模块/服务扩展，在同一主体与对象底座上增加检查事项与监管能力 | 形成辖区内扩张，而非重新建设独立系统 |
| 第三方服务生态 | 后续可接入安全生产技术服务、维保、检测、专家等机构，在法定/授权范围内提供服务 | 形成生态层收入；暂不作为 V1 核心收入 |
| 数据收入 | 不作为 V1 主收入来源 | 数据存在长期战略价值，但原始政务/企业/个人数据受到权属、保密、个人信息和公共数据规则约束 |

## 8.1 商业飞轮 —— PROPOSED

一个县/区采购 → 建立辖区共同底座 → 企业/物业统一接入 → 持续产生自检数据 → 政府开始抽检/监督检查 → 形成行政检查历史 → 政府看到监管价值 → 其他乡镇/部门主动扩展 → 市级需要统一查看 → 形成更高层级扩展与采购。

商业核心不是“5000 家企业逐个签 SaaS”，而是“一个行政辖区成为一个商业单元”。

# 9. 明确的产品边界 —— FROZEN

- 不做单纯消防柜巡检 App。
- 不做通用资产管理平台。
- 不做纯企业内部安全管理 SaaS。
- 不做单纯二维码工具。
- 不做第一阶段的大型“智慧应急/城市治理”综合平台。
- 不替行政机关创设检查标准、检查周期或行政处罚。
- 不把企业自检记录冒充行政检查记录。
- 不把平台生成的任务视为独立的行政权力来源；所有行政检查必须有合法主体、合法事项、合法计划/程序依据。
- V1 商业切口锁定安全生产/应急管理；跨部门能力作为架构方向，而非立即扩张产品范围。

# 14. 给 Codex 的执行口径

从本文件开始，Codex 后续所有方案、数据库设计、接口设计、权限设计和代码任务都应默认以下前提：

- 先遵守 V1 产品边界，不主动扩大到通用巡检、智慧城市或综合治理。
- 先引用 Authority SSOT，再设计具体业务规则。任何没有权威来源的检查事项/周期，都必须标为“待确认”，不能由代码自行推断为法律要求。
- 企业自检与行政检查是两个不同事实来源、两条审计链；任何实现不得把两者合并成一个“检查结果”字段。
- 二维码仅作为对象数字身份入口，不得把二维码逻辑写死成某一个行业或固定检查表。
- 政府权限是法定权限，不是简单的组织层级继承；首期只实现单县、单监管部门的显式授权，后续启用乡镇/市级等账号时也必须通过显式策略表达权限。
- 县级试点采购和单位基础使用随试点覆盖只是已批准的验证策略；商业模式尚未最终冻结，不要在代码中写死收费模式、订阅价格、政府采购流程或跨部门扩张逻辑。
- 部门现场抽检由获授权人员扫码发起，不以前置计划任务或派单为系统门槛；扫码不是行政授权，合法主体、事项、人员、启动情形与程序依据仍需核验留痕。
- 后续开发必须遵循“文档 → 合同/SSOT → 数据模型 → 接口 → 测试 → 代码”的顺序。
