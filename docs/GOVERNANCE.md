# 文档治理规则

## 状态与优先级

`FROZEN`：用户明确批准、适用于软件产品的决定，正文只在 `ssot/` 维护。`PROPOSED`：方案或商业假设，不作为实现授权。`OPEN`：设计细节或外部事实待确认。`EXTERNAL INPUT`：由有权主体在实施时提供并核验，不属于产品方可冻结的行政内容。归档与研究仅供溯源。

冲突时，以**当前专题 SSOT** 为准；同级专题交叉冲突则暂停相关实现、在 `OPEN.md` 登记并请求用户裁定。`DECISIONS.md` 是导航，不覆盖专题正文。原交接稿是迁移基线，不得因其标题包含“冻结”而覆盖后续已批准变更。不得把“产品支持录入”解释成“平台有权制定行政规则”。

## 修改协议

1. 提出变更时指明受影响的专题、现行决定、建议文本及对首期的影响。
2. 只有得到用户明确批准后，才修改对应专题 `FROZEN` 内容，并同步修改 `DECISIONS.md` 与受影响的交叉引用；记录日期、来源及变更摘要。单纯排版修订不改变决策状态。
3. 尚未确认的方案放在 `OPEN.md`；来源调查放在 `research/`；县、部门、检查事项与程序材料放在 `implementation/`，标明来源、版本、效力期、适用范围、核验状态。
4. 开发前核对专题 SSOT 与相应外部输入是否齐备。没有依据时允许保存待确认状态，不可显示成行政已确认、依法检查或合规结论。
5. 后续模块遵循[文档 -> 契约 -> 代码](../AGENTS.md)：先确认产品决定及[根目录派生契约](../constras/README.md)，再补齐本次功能所需的接口、数据或交互细节，最后实现并测试。契约是已批准决定的可检验表达，不是另一份产品 SSOT；其中明确输入输出、状态、权限、失败行为及外部输入缺失时的边界。变更产品行为须先获批准并修改专题 SSOT，再同步契约与测试；实现细节变化则先更新受影响的契约与测试。模块契约随实际模块创建，不预置空文件。
6. 验证文档导航链接、状态与标题一致、Markdown 表格列数一致、无重复权威正文；代码评审还需核对文档、契约、实现及测试一致性。

每份专题文件标出状态、范围和交接稿章节来源。相同事实只在一份专题内规范表述，其他位置用链接引用。后续确需新增专题时先更新本地图；不按功能清单机械生成空文档。
